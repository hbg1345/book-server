## 1. 비교의 진짜 축은 "부하 생성 모델"

도구 선택에서 가장 먼저 볼 것은 기능 목록이 아니라 **가상 유저(VU)를 어떻게 만드는가**입니다.

### 스레드 기반 (JMeter, nGrinder)
VU 1명 = OS 스레드 1개. 직관적이고 디버깅이 쉽지만, 스레드마다 스택 메모리(기본 ~1MB)와
컨텍스트 스위칭 비용이 붙습니다. 한 머신에서 뽑을 수 있는 VU가 **수백~1천 수준**에서 막히고,
그 이상은 부하 생성기를 여러 대로 분산해야 합니다.

### 비동기·경량 스레드 기반 (k6, Gatling, Locust)
VU가 OS 스레드가 아니라 고루틴/액터/그린스레드 같은 **경량 태스크**입니다. 한 머신에서
**수만 VU**가 나오므로 노트북 한 대로도 꽤 큰 부하를 만들 수 있습니다.

> 이 차이가 "부하 생성기를 몇 대 준비해야 하나"를 좌우합니다. 개인 프로젝트에서는
> **분산 구성 없이 노트북 한 대로 끝나는가**가 실질적으로 가장 중요한 기준입니다.

## 2. Apache JMeter

2001년부터 이어진 사실상의 업계 표준. Java 기반 GUI 도구.

### 장점
- **압도적 자료량.** 막히면 검색으로 거의 다 해결됩니다. 국내외 블로그·강의·StackOverflow 답변이 가장 많습니다.
- **프로토콜 커버리지 최고.** HTTP 외에 JDBC, JMS, FTP, LDAP, SMTP, TCP까지. DB에 직접 쿼리를 날리는 부하도 가능합니다.
- **GUI로 시작 가능.** 코딩 없이 클릭으로 시나리오를 만들 수 있어 진입 장벽이 낮습니다.
- `-e -o report/` 옵션으로 **HTML 대시보드 리포트 자동 생성**. 발표 자료에 그대로 붙일 수 있습니다.
- 이력서·포트폴리오에서 가장 널리 인식되는 이름입니다.

### 단점
- **`.jmx`가 XML이라 Git diff가 사실상 읽히지 않습니다.** 스레드 수 하나 바꿔도 diff가 수십 줄 나옵니다. 코드 리뷰 대상이 되기 어렵습니다.
- **스레드 기반이라 무겁습니다.** 고VU에서 부하 생성기(=내 노트북)가 먼저 병목이 됩니다.
- **단계적 부하(stages)가 기본 기능에 없습니다.** Spike/BreakPoint를 하려면 스레드 그룹을 계단식으로 여러 개 쌓거나 JMeter Plugins(jpgc)의 Concurrency/Stepping Thread Group을 설치해야 합니다. → **이번 5가지 유형 과제에 직접 걸리는 단점**
- GUI 모드로 부하를 주면 안 됩니다(GUI 자체가 자원을 먹음). 작성만 GUI, 실행은 반드시 CLI(`-n`).

## 3. k6 (Grafana Labs)

Go로 만든 CLI 도구. 시나리오는 JavaScript(ES6)로 작성합니다.

### 장점
- **설치가 없습니다.** `docker run grafana/k6 run script.js` 한 줄로 끝납니다.
- **stages가 1급 기능.** Load/Spike/BreakPoint를 배열 몇 줄로 표현합니다.
  ```js
  stages: [
    { duration: '2m', target: 100 },   // 램프업
    { duration: '10m', target: 100 },  // 유지
    { duration: '2m', target: 0 },     // 램프다운
  ]
  ```
- **`thresholds`로 합격 기준을 코드에 박습니다.** "p95 < 500ms, 에러율 < 1%를 못 맞추면 실패"를 선언하면 종료 코드로 판정되어 **CI에 그대로 붙습니다.**
- JS 스크립트라 **Git diff가 읽히고 코드 리뷰가 됩니다.**
- 경량이라 노트북 한 대로 수만 VU가 나옵니다.

### 단점
- **기본 리포트가 CLI 텍스트입니다.** 그래프를 보려면 Grafana + InfluxDB/Prometheus를 따로 붙여야 합니다. → JMeter/Gatling 대비 가장 큰 약점
- 테스트 이력이 자동으로 쌓이지 않습니다.
- **HTTP/gRPC/WebSocket 중심**이라 JDBC 같은 프로토콜은 커버하지 않습니다.
- 브라우저 렌더링·JS 실행 시간은 측정하지 않습니다(순수 프로토콜 레벨). — 이건 사실 JMeter·Gatling도 동일합니다.

## 4. nGrinder (NAVER)

The Grinder를 기반으로 NAVER가 만든 오픈소스. 국내에서 널리 알려져 있습니다.

### 장점
- **웹 대시보드에 테스트 이력과 그래프가 자동으로 축적됩니다.** 여러 번 돌린 결과를 나란히 비교하기가 가장 편합니다. 튜닝 전/후 비교 자료를 만들 때 강력합니다.
- **국내 자료가 많고 한국어 문서가 있습니다.** 주변에 물어볼 사람이 있을 가능성이 높습니다.
- Controller가 Agent를 관리하므로 **분산 부하 생성이 구조적으로 자연스럽습니다.**

### 단점
- **Controller + Agent를 별도로 띄워야 합니다.** 부하 테스트를 하려고 서버를 하나 더 운영하는 셈입니다. 개인 프로젝트에서 이 오버헤드는 작지 않습니다.
- 스크립트가 **Groovy 또는 Jython**입니다. 생태계가 사실상 국내 한정이라 영어권 자료가 얇고, 막히면 검색으로 안 나옵니다.
- 스레드 기반이라 k6/Gatling 대비 부하 생성 효율이 낮습니다.
- 프로젝트 활동성이 전성기만 못합니다. 신규 도입 시 고려해야 할 지점입니다.

---

## 5. Gatling

Scala로 만들었고 DSL로 시나리오를 작성합니다. 비동기 기반이라 가볍습니다.

### 장점
- **HTML 리포트 품질이 가장 좋습니다.** 별도 세팅 없이 응답시간 분포, 백분위수, 시간대별 그래프가 예쁘게 나옵니다. **문서·발표용으로는 최강.**
- **DSL을 Java/Kotlin으로도 쓸 수 있습니다.** 이 프로젝트가 Java라 언어가 통일됩니다.
- **Gradle 플러그인**으로 `./gradlew gatlingRun` — 빌드 도구에 자연스럽게 통합됩니다.
- 비동기 기반이라 머신당 VU 수용량이 큽니다.

### 단점
- **학습 곡선이 가장 가파릅니다.** DSL 문법과 시뮬레이션 개념(injection profile, feeder 등)을 익혀야 합니다.
- **무료판은 분산 부하 생성을 지원하지 않습니다.** 여러 대로 부하를 나누려면 유료 Gatling Enterprise가 필요합니다.
- Scala 잔재가 남아 있어 스택 트레이스가 낯설 수 있습니다.

---

## 6. Locust

Python으로 시나리오를 작성하는 도구.

### 장점
- **시나리오를 Python 코드로 자유롭게 작성**합니다. 조건 분기, 외부 라이브러리 호출 등 복잡한 로직을 넣기에 가장 유연합니다.
- **실시간 웹 UI 내장** — 돌아가는 중에 VU를 늘리고 줄일 수 있습니다.
- 코드 기반이라 Git 친화적입니다.

### 단점
- **Python GIL 때문에 코어당 성능이 낮습니다.** 코어를 다 쓰려면 워커 프로세스를 여러 개 띄워야 합니다.
- 같은 VU 수 기준 k6/Gatling보다 부하 생성기 자원을 많이 먹습니다.

## 7. wrk / hey / bombardier — 이건 부하 테스트 도구가 아닙니다

명령어 한 줄로 특정 URL을 때리는 **벤치마크 도구**입니다.

- 👍 극도로 가볍고 즉시 실행됩니다. 단일 엔드포인트의 최대 처리량을 빠르게 재는 데 좋습니다.
- 👎 **"로그인 → 조회 → 장바구니 → 주문" 같은 시나리오를 구성할 수 없습니다.** 상태를 이어가는 사용자 흐름이 표현되지 않습니다.

빠른 확인용 보조 도구로는 유용하지만, 이 문서의 5가지 테스트 유형을 수행할 수는 없습니다.

## 8. 기준별 종합

### 🎯 5가지 유형(Load/Endurance/Stress/Spike/BreakPoint) 표현력
1. **k6** — `stages` 배열로 5종을 파일 하나에 표현
2. **Gatling** — injection profile로 표현력 충분
3. **Locust** — 코드로 구현 가능하나 직접 짜야 함
4. **nGrinder** — 웹 UI 설정, 단계적 부하는 제한적
5. **JMeter** — 기본 기능만으로는 어렵고 플러그인 또는 계단식 스레드 그룹 필요

### 📊 리포트 품질 (세팅 없이 바로)
1. **Gatling** (압도적) → 2. **JMeter**(HTML 대시보드) ≈ **nGrinder**(웹 대시보드, 이력 축적) → 4. **Locust** → 5. **k6**(CLI 텍스트)

### ⚡ 부하 생성 효율 (머신당 VU)
1. **k6** ≈ **Gatling** → 3. **Locust** → 4. **JMeter** ≈ **nGrinder**

### 🔧 시작하기까지의 마찰
1. **k6** (docker 1줄) → 2. **JMeter**(JAR 다운로드) ≈ **Locust**(pip) → 4. **Gatling**(Gradle 설정) → 5. **nGrinder**(Controller+Agent 서버)

### 🎓 학습·취업 가치
1. **JMeter** (가장 널리 인식됨) → 2. **k6**(빠르게 표준화 중) ≈ **Gatling** → 4. **Locust** → 5. **nGrinder**(국내 한정)

### 🔁 CI 자동화
1. **k6** (thresholds → 종료 코드로 pass/fail) → 2. **Gatling**(assertion 지원) → 3. **JMeter** → 4. **Locust** → 5. **nGrinder**(서버 상주 구조라 CI와 궁합 나쁨)

## 9. 이 프로젝트(book-server) 관점 추천

| 당신이 가장 중시한다면 | 추천 |
|---|---|
| **5가지 유형을 코드로 깔끔하게 + CI 자동 판정** | **k6** |
| **세팅 없이 발표·문서용 그래프** | **Gatling** |
| **표준성 · 자료량 · 주변에 물어볼 사람** | **JMeter** |
| **테스트 이력을 웹에 축적, 튜닝 전/후 비교** | **nGrinder** |
| **복잡한 시나리오 로직(분기·외부 연동)** | **Locust** |

**정리:**
- 이번 목표가 "5가지 유형을 제대로 돌려보는 것"이므로 **k6가 1순위**입니다. JMeter로 Spike/BreakPoint를 하려면 스레드 그룹을 계단식으로 쌓거나 플러그인을 깔아야 하는데, 그게 XML로 들어가면 프로파일을 조정할 때마다 비용이 큽니다.
- 다만 **"주변 사람들이 JMeter를 쓴다"는 것도 정당한 선택 이유입니다.** 막혔을 때 물어볼 사람이 있고 결과물 형식을 남들이 알아본다는 건 개인 프로젝트에서 무시하기 어려운 장점입니다.
- **리포트 그래프가 결과물의 핵심**이라면 Gatling이 가장 유리합니다. 이 프로젝트가 Java라 언어도 통일됩니다.

## 10. 도구와 무관하게 주의할 점

### 부하 생성기의 위치가 결과를 왜곡합니다
노트북에서 부하를 주면 트래픽이 **가정용 인터넷 회선**을 통해 나갑니다. VU를 올리다 보면
어느 순간 Cloud Run이 아니라 **회선 대역폭이나 노트북 CPU가 먼저 한계**에 닿습니다.
그때 측정된 "한계점"은 서버 성능이 아니라 내 인터넷 속도입니다.

**판별법:** 부하 도구의 에러율·응답시간은 나빠지는데 **Cloud Run 콘솔 지표는 멀쩡하다면**
병목은 서버가 아니라 부하 생성기 쪽입니다. 이 경우 같은 리전의 GCP VM에서 부하를 주면 해소됩니다.

### 로컬 측정값은 서버 성능이 아닙니다
`docker compose`로 띄운 로컬 스택을 때리면 부하 생성기·앱·DB가 **같은 CPU를 나눠 씁니다.**
병목이 어디인지 섞여버려서 절대 수치로 쓸 수 없습니다.
로컬은 **스크립트가 제대로 도는지 확인하는 용도**(5 VU / 1분)로만 쓰고, 실측은 배포본에서 합니다.

### `GET /api/books`는 부하 대상으로 부적절합니다
현재 이 엔드포인트는 **페이지네이션이 없습니다**(`BookController.java:43`).
시드 데이터가 103,056권이므로 한 번 호출하면 전체를 JSON으로 직렬화해 내려줍니다.
여기에 부하를 주면 서버가 수 초 만에 OOM으로 죽고, 측정 결과는 "이 엔드포인트가 설계상 터진다"는
사실 하나뿐입니다. 읽기 부하는 **`GET /api/books/{uuid}` 상세 조회**를 사용합니다.

### 콜드스타트를 측정에 섞지 않습니다
Cloud Run은 유휴 시 인스턴스를 0으로 내립니다. 부하 테스트 첫 요청은 JVM 콜드스타트(수 초)를
포함하므로, **워밍업 구간을 두고 그 구간의 결과는 집계에서 제외**해야 합니다.
반대로 콜드스타트 자체를 측정하고 싶다면 그건 별도 테스트로 분리합니다.

## 참고: 5가지 테스트 유형

| 유형 | 부하 프로파일 | 확인하는 것 | 일반적 지속 시간 |
|---|---|---|---|
| **Load** | 목표 VU 유지 | 평상시 응답시간(p95/p99), 에러율 | 1시간 |
| **Endurance(Soak)** | 낮은 VU 장시간 유지 | 메모리 누수, 커넥션 풀 고갈 | 8시간 이상 |
| **Stress** | Load의 3~5배 | 장애 발생 여부, **부하를 내렸을 때 정상 복구되는지** | 30분~1시간 |
| **Spike** | 순간 10~20배 후 즉시 하강 | 죽지 않고 버티는지, 회복까지 걸리는 시간 | 10분 |
| **BreakPoint** | VU를 계속 증가(유지 구간 없음) | **시스템의 한계점 = 최대 처리량** | 20~40분 |

> **BreakPoint를 가장 먼저 돌리는 것을 권합니다.** 한계점을 알아야 Load/Stress의 "적정 VU"를
> 근거 있는 숫자로 정할 수 있습니다. 그전에는 100 VU 같은 값을 임의로 찍는 수밖에 없습니다.
